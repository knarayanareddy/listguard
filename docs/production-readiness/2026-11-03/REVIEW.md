# ListGuard production-readiness review

## Scope and verdict

Reviewed revision: `3f5778479f3c4d900b49f5b676da62a204d09cf5`. Stage: implemented deterministic moderation prototype with a FastAPI service, SQLite receipts, a CLI, tests and a browser review desk. **Not ready for an exposed production deployment. Runtime checks: NOT RUN.** The most immediate blockers are malformed installation input, missing active CI, an intentionally external authentication boundary, and signing-key storage that contradicts the documented deployment separation.

This review sampled the manifest, requirements, CLI, README and test excerpts. Four additional pinned files were fetched: API, storage, policy and dashboard. Only the cited portions of these large files were traced. No installation, test suite, endpoint request, browser session, dependency audit or deployment was executed. There are no Actions results in the snapshot; that is not evidence of passing tests.

## Architecture and product boundary

The [CLI](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/main.py#L154-L184) creates an application instance and passes it to Uvicorn. The [application factory](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/api.py#L1067-L1125) constructs or accepts a receipt store and evaluator. Moderation validates the evaluator output before storing a system receipt; human decisions append receipts through a separate handler. SQLite and the signing key are security-sensitive persistent state.

The [README](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/README.md#L57-L78) explicitly makes the reference classifier deterministic and any future model advisory. This is not image-model inference or a demonstrated universal detector. Listing content, OCR and metadata are untrusted inputs. The product must remain content-only: none of the proposed work authorizes account bans or other sanctions against sellers.

## Findings ledger

### LG-01 — High, confirmed static: installation file contains pasted workflow content

[`requirements.txt:7-58`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/requirements.txt#L7-L58) includes `=== END FILE ===`, a `=== FILE: .github/workflows/ci.yml ===` delimiter, and YAML after six dependency pins. These are not valid requirement entries. The README's documented requirements installation therefore has malformed input; the exact pip diagnostic was not reproduced. The complete, nontruncated file tree has no `.github/workflows/ci.yml`: pasted YAML in a requirements file is not an active workflow. Restore the two distinct files and prove installation and CI actually execute.

### LG-02 — High deployment blocker, confirmed static boundary: review identity is caller supplied

The [receipt and override handlers](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/api.py#L1174-L1250) accept requests without an authentication dependency in the inspected factory. The dashboard submits an editable [`operator_id`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/web/templates/index.html#L997-L1036). The README correctly [warns that this is not authentication](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/README.md#L164-L175). No deployed gateway was inspected, so an actual public exposure is unverified. Production must authenticate callers, authorize receipt access and override rights, and derive attribution from the trusted principal rather than trusting that body field. Keep a loopback-only development mode explicitly separate.

### LG-03 — High, confirmed static: supplied signing secret is persisted with the database

[`storage.py:340-380`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/storage.py#L340-L380) calls signing-key initialization and writes `self._provided_signing_key` or a generated key, base64-encoded, into `audit_metadata` when first creating metadata. No external-mode branch guards that write. The [constructor](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/storage.py#L197-L235) accepts all three verification modes. This undermines the README's [separate secret-management prescription](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/README.md#L177-L194): access to a database copy can also expose the HMAC key. Base64 is not encryption. Actual compromise is not alleged. Separate production signing material from receipt storage, define key identifiers and rotation, and retain an external integrity checkpoint.

### LG-04 — High, confirmed static policy defect: a custom brand verifier can suppress weapon priority

The evaluator [detects weapon and injection reasons, then selects custom-verifier counterfeit first](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/policy.py#L738-L776). In that first branch, `reasons` contains only brand reasons. The later router [escalates to weapon only when weapon reasons survive](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/policy.py#L470-L495). A custom verifier returning counterfeit without weapon reasons can therefore turn a detected weapon into counterfeit/queue instead of weapon/block. This contradicts the documented precedence; it does not mean the default verifier necessarily follows this path. Preserve independently detected reasons and enforce strongest-policy priority after combining signals. Add a targeted custom-verifier regression case.

### LG-05 — Medium, confirmed static: incomplete demo fixture sets can pass

[`collect_demo_cases`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/main.py#L100-L151) skips each missing named fixture and rejects only an entirely empty set; successful evaluation returns zero. A directory containing one fixture can therefore appear to complete the canonical four-case demo. Expected action assertions are also not present in this CLI loop. Make completeness and expected outcomes explicit, or clearly label a separate partial-demo mode. This matters for a release smoke gate, not as proof that every existing policy test is defective.

### LG-06 — High, confirmed static: receipt retrieval does not verify its signature

The concrete store's [`get_receipt`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/storage.py#L810-L829) returns `_parse_receipt(...)` without calling the available signature verifier. The API's [`_get_receipt`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/api.py#L352-L392) returns a coerced receipt without an independent integrity check. [`verify_chain`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/storage.py#L986-L999) checks links, not signatures; a single schema-valid modified receipt with no predecessor is not rejected by that check. Actual tampering was not exercised. Production read and override paths must fail closed on unauthenticated receipts, rather than equating valid JSON or a linked history with authentic content.

### LG-07 — High, confirmed static: singular rifle pattern has a leading-space defect

The weapon regex includes `shotgun| rifle|rifles` at [`policy.py:150-155`](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/policy.py#L150-L155). The singular alternative requires a literal space; the word boundary outside the alternatives does not repair that requirement. Normalized values are stripped and joined with newlines at [lines 284–296](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/policy.py#L284-L296). A title consisting of `rifle`, with no other weapon cue, is consequently not matched by these weapon patterns. End-to-end behavior is unrun. Correct the expression and test singular/plural words at start/end, punctuation and independent metadata fields without broad substring overblocking.

## Five-discipline assessment

- **Code correctness:** explicit schemas, parameterized receipt lookup and append-oriented handlers are useful foundations. LG-04 demonstrates why both default and custom dependency paths need invariant tests. The broad compatibility helpers in the API were not exhaustively traced.
- **Automation:** four test modules exist, with strict pytest options in the manifest. Their presence is not a successful execution. LG-01 prevents relying on the documented environment setup or pasted CI. Build the distributable too: templates, policy JSON and fixtures live outside the included `listguard*` package pattern; installed-wheel resource availability is an unverified packaging risk.
- **DevOps:** no active workflow or deployment configuration appears in the pinned tree. The health endpoint [returns a constant status](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/listguard/api.py#L1127-L1129), not a database-readiness or signature-integrity check. SQLite backup consistency, concurrent writers, disk exhaustion, restoration and key recovery need measured acceptance.
- **OWASP/security:** identity spoofing and broken object-level authorization are the main exposure questions. Receipt identifiers are not authorization. Assess request-size limits, rate limiting, log redaction, dependency advisories and trusted-proxy configuration; none was tested. Signing must resist database-only compromise, while an external checkpoint addresses whole-history replacement.
- **UI/UX/accessibility:** [textContent rendering](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/web/templates/index.html#L922-L934) avoids one direct HTML-insertion pattern. [A/O shortcuts](https://github.com/knarayanareddy/listguard/blob/3f5778479f3c4d900b49f5b676da62a204d09cf5/web/templates/index.html#L1098-L1122) ignore editing fields and modifier keys, but still deserve consequence-aware testing. Verify focus, screen-reader feedback, failed submissions, duplicate reviews and confirmation of server-persisted state. No visual accessibility verdict is claimed.

## Owner decisions and evidence limitations

Identify deployment exposure, identity provider, reviewer roles, tenant boundaries, retention and appeal policy, acceptable classification error rates, recovery objectives and managed signing service. Confirm whether custom verifiers are permitted. No external model is required to harden the deterministic path. Signing separation and gateway enforcement must be established before production use, not assumed from documentation. See [REMEDIATION_PLAN.md](REMEDIATION_PLAN.md) for dependencies and acceptance.
